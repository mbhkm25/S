## Provenance and scope

- **UI action result:** `SanadAgentActionCard.tsx` formerly showed the same `تم التنفيذ` pill for completed personal transactions and completed commercial drafts, although a commercial action writes only a SANAD document draft. `sanadOperationalState.ts` now separates review, approved, executing, cancelled, failed, completed draft with verified `document_id`, completed personal transaction with verified `transaction_id`, and unknown/no-reference states. The UI requires the latest server-authoritative action read before enabling the approval button; authoritative server-side version/ownership checks remain unchanged.
- **UI source display:** `sanadSourceDisplay.ts` groups available numeric strings without rounding source fractions; formats only explicitly qualified ISO timestamps, validates calendar dates, and uses `Asia/Aden` only on timestamps containing an explicit `Z` or offset. Bad/ambiguous dates remain raw with a label, not assigned an invented timezone. `SanadAgentResponseBlocks.tsx` isolates monetary/date/currency directional spans in Arabic RTL.
- **Existing backend statement copy:** Production `sanad-ai-agent-v1` version **6** uses `supabase/functions/_shared/sanad-agent-presentation.ts`, whose previous `money()` formatted copied ERP statement totals to **at most 2dp** and defaulted missing values to zero. The PR updates the *repository source* to keep the decimal fraction already available from parsed JSON and use `—` for absent totals. **This server-source change is NOT live** until the separately approved Edge Function release gate; a Web/PWA-only deploy would not activate it. Do not imply a green frontend build or local site preview proves a new copied-statement payload.
- **Canonical ERP precision:** Production `get_business_erp_customer_statement_v1` safely parses existing snapshot Amount into PostgreSQL numeric and aggregates by currency. Its existing JSON output is later parsed as JavaScript `number`; beyond safe numeric magnitude/precision, the original decimal text cannot be reconstructed from a rounded JS number. This PR improves *presentation of the precision received*, **not** guaranteed full original ERP precision. End-to-end exact decimal strings require a separate backward-compatible, reviewed RPC contract with original `numeric::text` fields, independent auth/DB migration verification and a separate release. Do not replay old migrations to implement it.
- **Today Work Items:** Production `get_my_sanad_today_v1` filters by `recipient_user_id = auth.uid()`, open/in-progress state and optional authorized `business_id`; existing payment-inbox Work Items contain a source reference, status and backfill metadata but **not** party name, amount or currency. The UI now distinguishes each row by an existing authorized reference and explicitly signals unavailable context. No cross-tenant client join, fabricated names/amounts or new DB write. Enriching details requires a reviewed additive server read-model gated by current permissions and #376 D-ARCH, not an ad-hoc browser join.
