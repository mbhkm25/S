# Business Financial Routing Foundation

## Status

Implemented on Supabase production and documented on branch:

`feature/business-financial-routing-foundation`

This package is phase 1 of the SANAD real-time business payment inbox roadmap. It establishes the durable financial identity layer only. It does not yet route operations or create cashier inbox items.

## Product objective

A business account must be matchable from financial notices without assuming that every provider exposes the same field as an account number.

Supported identifiers:

- account number;
- wallet number;
- customer/financial line;
- merchant or Haseb point;
- terminal number;
- linked phone number;
- IBAN;
- another explicit identifier.

The purple Haseb transaction-history template is classified as **الكريمي حاسب** (`kuraimi_haseb`). For this provider, a merchant/Haseb point may be more useful for routing than the account number shown at the top of the screenshot.

## Schema

### `financial_entities`

Canonical registry and prompt alignment. It contains display values, aliases, routing state, sort order and provider metadata.

### `business_financial_accounts`

Business-owned financial identity:

- business;
- canonical financial entity;
- raw entity name for `other`;
- account holder/beneficiary name;
- internal account label;
- multicurrency flag;
- routing state;
- verification lifecycle;
- soft archive state;
- creator and audit timestamps.

### `business_financial_identifiers`

One account can have multiple typed identifiers. Normalized values are generated by PostgreSQL and indexed for the future routing engine.

### `business_financial_account_events`

Immutable lifecycle audit trail for migration, creation, update, archive, routing-state and verification-state events.

## Normalization

`normalize_financial_identifier(text)`:

- converts Arabic and Persian digits to Latin digits;
- removes spaces, separators and non-alphanumeric characters;
- lowercases Latin characters;
- preserves leading zeroes.

`normalize_financial_name(text)`:

- converts Arabic/Persian digits;
- removes Arabic diacritics and tatweel;
- normalizes common Alef/Yaa/Hamza variants;
- removes punctuation;
- collapses whitespace;
- preserves the raw source value separately.

Normalization is deterministic and database-owned. AI output is never treated as a normalized key directly.

## Fast matching indexes

The routing-critical index is:

`business_financial_identifiers_fast_match_idx`

It indexes the normalized identifier and includes account, identifier type and currency for active routing-enabled identifiers.

A second partial index supports provider plus normalized account-holder matching for the later fallback path.

The Supabase performance advisor was run after DDL. Missing indexes reported for the new audit/ownership foreign keys were added in migration `20260731100440_business_financial_routing_fk_indexes.sql`.

## Security model

- RLS is enabled on all four new tables.
- Authenticated direct reads are limited to the business owner or platform administrator.
- Direct inserts, updates and deletes are not granted to the client.
- Writes use guarded RPCs that verify `auth.uid()` and business ownership.
- Internal normalization, projection, cache synchronization and entity-resolution functions are not executable by `anon` or `authenticated`.
- Public profile compatibility JSON excludes canonical account UUIDs, internal routing flags, identifier arrays and audit data.
- Archiving is soft: identifiers stop routing while audit history remains intact.

Supabase's generic advisor reports authenticated `SECURITY DEFINER` RPCs even when they contain ownership checks. These RPCs are intentionally authenticated entry points and validate the actor before any mutation. The wider project still has unrelated pre-existing security-advisor warnings that are outside this package.

## Compatibility strategy

The old UI contract stored accounts under:

`business_profiles.profile_sections.financial_accounts`

That JSON is now a public-safe compatibility cache, not the source of truth.

The canonical tables are written first. The cache is regenerated after successful writes and archives. `update_business_profile` preserves the canonical cache even when a client submits a full `profile_sections` object, so general profile editing cannot restore stale account data or bypass the normalized write path.

Existing clients can continue calling:

- `upsert_business_financial_account`
- `delete_business_financial_account`

The canonical UI/API uses:

- `get_financial_entities`
- `get_business_financial_accounts`
- `upsert_business_financial_account_v2`
- `delete_business_financial_account`

## Management UI

A new collapsible **الحسابات المالية والتوجيه** center is exposed in business management. It supports:

- canonical provider selection;
- account-holder name;
- internal label;
- multiple typed identifiers;
- optional currency per identifier;
- multicurrency state;
- routing enable/disable;
- edit and audit-preserving archive;
- a specific operational hint for `kuraimi_haseb` merchant points.

The legacy accounts tab remains temporarily available as a compatibility path and now writes through the normalized tables.

## Phase 2 boundary

The next phase should add explicit operation columns and extraction confidence per field:

- receiver name and normalized receiver name;
- receiver account/identifier and normalized value;
- sender fields;
- document template and transaction direction;
- per-field confidence and evidence;
- support for merchant-point and credited-account roles.

No automatic business routing should be enabled until phase 2 extraction is evaluated in shadow mode against redacted real notices.
