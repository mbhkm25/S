# Stage 2D — تجهيز الحساب والتصنيف من المحادثة

## سبب الحزمة ونطاقها

كانت المحادثة تقرأ الحسابات والتصنيفات وتجهز الحركة فقط، فتتوقف عند عدم وجود حساب. هذه الحزمة تضيف تجهيز حساب أصول شخصي أو تصنيف دخل/مصروف داخل المحادثة وبطاقة المراجعة الحالية. لا تدعم «أي كتابة» عامة، ولا إنشاء حسابات التزامات أو أطراف أو عملات جديدة، ولا رصيدًا افتتاحيًا أو ربط حساب خارجي أو تصنيفًا فرعيًا. توسيع هذه المتطلبات يحتاج عقدًا محددًا لكل نوع.

الفرع `stage2d/chat-finance-setup-20260927` مستقل، ويجمع محليًا متطلبات #413 و#417 دون تعديل فرعيهما أو #414. طلب هذه الحزمة تراكمي فوق #417 ويحتوي متطلب #413؛ **لا تدمجه إلى فرع الواجهة**. بعد اعتماد ودمج #413 و#417، أعد توجيه base إلى main وراجع الفرق المتبقي. لا توجد تغييرات Bridge.

## مسار المستخدم داخل التطبيق الفعلي

1. افتح مشروع **شخصي** في سند، واطلب: «أضف حساب صندوق نقدية بعملة YER».
2. يقرأ المساعد الحسابات أولًا. إن غاب الاسم أو العملة يسأل عنهما، وإن وجدا لا يخمن بديلًا. يظهر الاسم والعملة ونوع الحساب ورصيده الافتتاحي صفر في بطاقة مراجعة.
3. تجهيز البطاقة لا ينشئ الحساب. زر اعتماد يستدعي عقد الاعتماد الحالي بالإصدار المتوقع ثم أمر إنشاء الحساب الحالي، برصيد افتتاحي صفر يحدده الخادم.
4. يمكن طلب «أضف تصنيف مصروف باسم وقود»، واعتماد بطاقة منفصلة. التصنيف اختياري؛ عدم وجوده لا يوقف تجهيز المصروف.
5. بعد الاعتماد اكتب «تابع المصروف». يقرأ المساعد المعرّفات الحقيقية مجددًا ويجهز بطاقة المصروف من سياق المحادثة، ويسأل عما ينقص. لا يعد اعتماد الحساب اعتمادًا للمصروف، ولا ينفذ الحركة تلقائيًا.

يعرض النوعان الجديدان «إلغاء وإعادة تجهيز» بوضوح بدل الادعاء بوجود محرر حقول على نفس المعرف. تعديل المصروف نفسه يحتفظ بمعرفه عبر #413/#417. لا تُعرض أداة تحرير الملاحظات القديمة للنوعين الجديدين.

## العقد والضمانات

- نوعان محددان في `sanad_agent_actions`: `personal_account_setup` و`personal_category_setup`، بنفس الأحداث وبطاقات المراجعة وWork Items والإلغاء والاعتماد.
- نفس `private.normalize_sanad_agent_action_v1` يتحقق من المصدر الشخصي المملوك النشط، والمرفقات، ومن قائمة حقول مغلقة؛ يعيد بناء المراجعة على الخادم. تمديد trigger المصدر دون إضعاف ثبات مصدر الإجراء.
- الأداتان `action_prepare_personal_account` و`action_prepare_personal_category` تجهزان فقط؛ لا تعرضان أمر إنشاء الحساب مباشرة للنموذج، ولا أدوات اعتماد/تنفيذ. يجب نجاح قراءة قائمة المتطلبات أولًا في نفس الدور.
- الاعتماد يعيد التحقق من المصدر والحمولة، ثم يمرر حقولًا محددة فقط لأوامر `create_personal_finance_account_v1` و`create_personal_finance_category_v1` الحالية. لا تغيير على هذه الأوامر العامة أو سياسات RLS.
- قفل معاملات على المستخدم يمنع اعتماد بطاقتين متزامنتين في محادثتين لإنشاء حساب/تصنيف بالاسم والعملة/النوع نفسيهما. المتطابق الموجود، بما فيه المؤرشف، يوقف الإضافة بدل إعادة تفعيله أو نسخه؛ واجهة الخطأ عربية.
- منع التكرار هذا يخص مسار المحادثة؛ لا يغير سياسة تكرار الحسابات في الشاشات الأخرى أو يجعل القفل ضمانًا لجميع كتابات النظام.
- إعادة اعتماد الإجراء المكتمل تعيد نتيجته نفسها. رفض نسخة قديمة/فارغة، مالك آخر، مصدر تجاري/مؤرشف، أو حقول رصيد/ملكية/metadata محقونة.
- إصلاح بناء العرض: نتيجة أداة فاشلة أو بلا معرف UUID محفوظ ونوع وإصدار وحالة مراجعة صحيحة لا تولّد بطاقة اعتماد فارغة، ولا تلحق بها عبارة توحي بإنشاء المسودة. هذا يصلح مسارًا محتملًا لبطاقات الخطأ السابقة، وليس إثباتًا لسبب كل بطاقة تاريخية.
- لا ERP، لا Bridge، لا ترحيل مصروف، ولا نظام تخزين موازٍ.

- `SANAD_TEST_SETUP_REGRESSION=1 npm run test:draft-contract`: 56 حالة ناجحة بعد تثبيت migration الجديدة، بما فيها تطابق الأنواع السابقة ومحرر المصروف.

- GitHub PostgreSQL 17: نجحت 56 حالة إعداد تشمل تنافس معاملتين مستقلتين، بجانب 59 حالة انحدار وصفر استدعاءات تنفيذ مالية. نتائج job رقم 108588127265؛ راجع أيضًا فحوص رأس الفرع النهائي.
- لم يُشغَّل متصفح أو معاينة أو اختبار واجهات. لم يُستدعَ نموذج مدفوع أو أي حساب/حركة فعلية. قبول الشكل والتجربة الحقيقية للمستخدم.

## حاجز التشغيل والنشر

**نسخ كود React وتشغيل 3000 وحدهما لا يضيفان أدوات إلى المساعد السحابي.** يلزم، بعد الموافقات التشغيلية، تثبيت عقود قاعدة البيانات ثم تحديث Edge ثم اختبار التطبيق المحلي. لم تنفذ هذه الحزمة أي تغيير على Supabase الإنتاجية أو نشر Web/Edge.

الترتيب المحدد، دون `db push` جماعي أو إعادة تطبيق migrations قديمة:

1. `20260927064224_stage2d_personal_expense_draft_edit_v1.sql` من #413، إن لم تكن مثبتة.
2. `20260927075434_stage2d_personal_expense_editor_capability_v1.sql` من #417، إن لم تكن مثبتة.
3. `20260927130000_stage2d_chat_personal_setup_v1.sql` من هذه الحزمة؛ معاملة واحدة.
4. تحديث `sanad-ai-agent-v1` بكامل اعتماداته المشتركة من نفس commit، دون تعطيل التحقق من JWT أو تغيير أسرار/إعدادات الأمان.
5. تشغيل **التطبيق الأصلي** محليًا `npm.cmd run preview:local` ثم اختبار المستخدم. الدمج والنشر النهائي للواجهة بيد المستخدم.

قبل/بعد تركيب SQL، تحقّق قراءة فقط من سجل migrations ومن تعريفات normalizer/approve/origin guard/descriptor والأوامر الحالية. راجع grants وRLS دون تعديلها. بعد التركيب descriptor الشخصي يجب أن يعرض خمسة إجراءات، والتجاري إجراءً تجاريًا فقط. لا تختبر اعتماد مصروف على بيانات حقيقية. اعتماد حساب صفري أو تصنيف اختبار يكتب بيانات إعداد فعلية؛ لا يتم تلقائيًا، ويُجرى فقط في حساب اختبار مخصص يختاره المالك.

عند التراجع: أوقف إتاحة أدوات التجهيز الجديدة في Edge أولًا؛ أبق عقود قراءة/اعتماد السجلات الموجودة. لا تحذف النوعين من CHECK مع وجود بيانات ولا تحذف حسابات أو تصنيفات أو مسودات المستخدم.

## قائمة قبول المستخدم بعد جاهزية الخادم

- اطلب حسابًا بدون عملة: سؤال توضيحي، لا عملة مفترضة ولا بطاقة ناقصة.
- جهز الحساب ثم ألغِ البطاقة: لا حساب جديد. أعد الطلب واعتمد في حساب اختبار مخصص: حساب واحد برصيد صفر، دون حركة مالية.
- أعد الطلب: يقرأ الموجود ولا يكرر إنشاءه. تحقق أيضًا من العودة للبطاقة المكتملة وعدم تكرار الاعتماد.
- جهز تصنيف دخل وتصنيف مصروف؛ مراجعة النوع واضحة. لا يجبرك على إنشاء تصنيف للمصروف.
- اكتب «تابع المصروف»: بطاقة مصروف بالحساب الصحيح والعملـة الصحيحة؛ راجع/عدّل ثم ألغِ، **لا تعتمد حركة مالية للاختبار**.
- جرّب إلغاء وإعادة تجهيز حساب بمعلومات مختلفة؛ لا يصف العملية كتعديل لنفس المعرف.
- افحص العربية/RTL والالتفاف والأزرار على الحاسوب والموبايل في التطبيق الحقيقي، وأرسل اللقطة والنتيجة.
