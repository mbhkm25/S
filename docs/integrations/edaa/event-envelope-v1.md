# ERP Event Envelope v1

Status: SANAD NEXT ingestion contract v1.

This contract is ERP-neutral. Edaa is the first adapter, but Edaa table names must remain inside the adapter/normalizer boundary.

## HTTP boundary

Development Edge Function:

`POST /functions/v1/sanad-erp-ingest-v1`

Device authentication headers:

- `x-sanad-device-id`
- `x-sanad-device-token`

The token is an installation credential. It is not a SANAD user JWT, ERP password, SQL password or shared merchant password.

## Envelope

```json
{
  "event_id": "stable-event-id",
  "adapter_code": "edaa",
  "adapter_version": "v1",
  "event_schema_version": 1,
  "entity_type": "sale",
  "source_record_id": "1306",
  "revision": "source-revision",
  "captured_at": "2026-09-14T09:00:00Z",
  "business_date": "2026-09-14",
  "source_enter_time": null,
  "payload": {},
  "integrity": {}
}
```

## Field semantics

### `event_id`

Stable retry identity generated by the Bridge. Re-sending the same logical observation must reuse the same event ID.

### `adapter_code` / `adapter_version`

Identify the ERP adapter and its implementation version. Versioning allows cloud compatibility during phased Bridge upgrades.

### `event_schema_version`

Version of the envelope/payload contract understood by the ingestion/normalization pipeline.

### `entity_type`

Canonical source entity category such as `sale`. It is not a raw table name.

### `source_record_id`

ERP-local record identity. It is not globally unique and is always interpreted within the registered source instance.

### `revision`

Stable identity for one observed version of a source record. Updates/corrections must not silently overwrite an earlier raw observation.

### `captured_at`

Time the Bridge captured the observation. This is provenance time, not automatically the business transaction time.

### `business_date`

Optional business date from the ERP when semantically known.

### `source_enter_time`

Optional source-entered timestamp when reliable. Edaa fields known to contain invalid legacy timestamps must not be promoted as authoritative time.

### `payload`

Raw adapter payload. The ingestion endpoint stores it as evidence and does not pretend it is the SANAD canonical domain model.

### `integrity`

Adapter integrity observations such as whether related sale/accounting/inventory evidence was found. Missing legacy links can be represented as warnings.

## Server-derived identity

The client does not choose a trusted SANAD `business_id`, `location_id`, `connection_id` or `source_instance_id` inside the envelope. The cloud derives those values from the authenticated Bridge device registration.

This prevents a Bridge from claiming another business/source merely by changing JSON fields.

## Idempotency

The database enforces:

- unique `event_id`;
- unique `(source_instance_id, entity_type, source_record_id, revision)`.

Expected ACK states:

- `accepted` — first accepted observation;
- `already_accepted` — same event ID was already accepted;
- `duplicate` — same source entity/revision was already accepted under its existing event identity.

If an existing `event_id` is reused for materially conflicting source identity/payload, ingestion returns an `event_id_conflict` rather than silently accepting it.

## ACK example

```json
{
  "ok": true,
  "status": "accepted",
  "event_id": "stable-event-id",
  "receipt_id": "cloud-receipt-uuid",
  "received_at": "2026-09-14T09:00:01Z"
}
```

A Bridge may retry after network uncertainty. A retry must not create a second logical raw event.

## Security rules

- never log the device token;
- only a hash of the device token is stored server-side;
- credentials are per Bridge device and revocable;
- raw event and credential tables are not directly readable by ordinary authenticated users;
- ingestion/normalization RPCs are service-side only;
- Phase 1 remains ERP read-only.

## Edaa normalization boundary

The exact Edaa `ibex-1` sale bundle shape has now been verified from a real transaction fixture. Edaa-specific field interpretation remains inside the adapter/normalizer boundary; the generic envelope does not expose Edaa table semantics as platform-wide concepts.

The evidence-based mapping and review rules are documented in:

`docs/integrations/edaa/sale-normalization-v1.md`

For the verified v1 sale path:

- `payload` carries the complete Edaa transaction bundle;
- `integrity` carries the bundle integrity object;
- `source_record_id` is the source sale ID;
- `entity_type` is `sale`;
- the normalizer preserves raw currency IDs/exchange values and resolves ISO currency only through an explicit source-instance mapping;
- `AccountID` is never promoted to canonical customer identity by itself;
- invalid legacy timestamps such as the observed 1899 inventory timestamp are not treated as authoritative transaction time.

Production Bridge revisions must also become update-safe: capture-only values must not determine revision identity, and later ERP corrections must produce a new revision/raw observation rather than overwriting prior evidence.
